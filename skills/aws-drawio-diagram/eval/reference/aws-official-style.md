# The expected diagram style

`aws-official-style.png` — *Temenos Wealth Front Office on AWS*, an AWS Reference
Architecture reviewed 2023-01-06, © 2022 Amazon Web Services. 2000 × 1104 px.

Kept as the style exemplar for every `.drawio` case. It is the right kind of
reference precisely because **AWS drew it, not the skill under test**: a
standard generated by the tool being evaluated cannot fail it, and every defect
the generator has becomes part of the target. See `README.md` for the S3 icon
that went blank in the reference I first tried to generate.

The contract below is written out rather than left to the judge to infer from
pixels. Prose is diffable, reviewable, and gives the same answer twice; "look at
the picture and tell me if the style matches" does not.

---

## 1. The frame

The diagram is a *document*, not a bare canvas.

- **Title** top-left, large and bold — the workload, ending in "on AWS".
- **Subtitle** below it, one size down, naming the view: `VPC & Networking`. A
  diagram is one view of a system, and it says which.
- **One-sentence thesis** under the subtitle: *"This architecture makes use of
  AWS services to provide security and elasticity with low maintenance
  overhead."* It states the design intent, not the contents.
- **Horizontal rule** separating header from canvas.
- **Footer**: AWS logo, `Reviewed for technical accuracy <date>`, copyright, and
  `AWS Reference Architecture` centred in orange.
- **Annotation panel** down the right on a light grey field, visually separated
  from the canvas.

## 2. The comments

This is the element that distinguishes a reference architecture from a topology
drawing, and the reason this image was chosen as the standard.

- **Numbered badges** — white numeral on a blue rounded square — placed on the
  canvas *next to the thing they annotate*, with a thin leader line or bracket
  where the target would otherwise be ambiguous (badge 1 brackets down to
  CloudFront and API Gateway; badge 4 sits on the EKS boundary).
- **The right panel repeats each badge** and follows it with prose.
- **Numbering follows the architecture's reading order** — edge security (1),
  private ingress (2), ingress restriction (3), compute (4), AZ topology (5),
  service access (6), data durability (7). Not arbitrary, not
  alphabetical.
- **AWS service names are bold inside the prose.**
- **The comments carry design rationale, never restate the picture.** Compare:

  | ✗ what a label already says | ✓ what the reference actually says |
  |---|---|
  | "Amazon EKS runs containers" | "**Amazon EKS** containers run on **AWS Fargate**, **Amazon EC2**, or a combination of both." — alternatives |
  | "There are two Availability Zones" | "This architecture diagram shows two Availability Zones, but the architecture can be extended to three." — scope of the drawing |
  | "API Gateway is present" | "**Amazon API Gateway** private endpoints can be used for secure on-premises access through a VPN or through **AWS Direct Connect**." — why it is there |

  Each one answers *why is this here*, *what else could go here*, or *what is
  this drawing not showing*. A comment that a reader could have derived from the
  icons earns nothing.

## 3. Containers

Nesting is shown by border style and a badge, never by colour fill alone.

| Container | Border | Badge / label |
|---|---|---|
| AWS Cloud | thin solid dark | `aws` logo badge top-left, label to its right |
| VPC | solid green | green cloud-in-box badge, green label |
| Availability Zone | dashed orange | orange label, repeated at **top and bottom** of the band |
| Amazon EKS | solid dark red | EKS badge, red label |
| Component group (UXP, API layer, FIN, INT) | dashed orange | label below the group |
| Logical grouping (`integration services`) | grey fill, no border | grey label, bottom-centre |

Notes:

- **Two VPCs** appear — one for internet ingress, one for Direct Connect. A
  single VPC is not assumed.
- The AZ bands **span horizontally across** the EKS box rather than sitting
  inside one column, so a component can be read as present in both zones.
- Subnet padlock glyphs sit on container edges.
- **No `Region` container.** The nesting is Cloud → VPC directly. Adding a
  Region is not a defect — the skill's own example does — but its absence here
  must not be scored as one.

## 4. Icons

- Resource icons are **filled squares with a white glyph**, in official AWS
  category colours: purple networking (CloudFront, Direct Connect, VpcLink), red
  security (WAF, Shield, ACM, Secrets Manager), orange containers (ECR, pods),
  magenta management (CloudWatch, MQ), green storage (S3), blue database (RDS).
- Colour carries category information. Icons are not recoloured for aesthetics.
- **Non-AWS actors are drawn differently on purpose**: flat dark-grey line
  drawings (people, server stack), no coloured square, and **placed outside the
  AWS Cloud boundary**. The visual language distinguishes "thing AWS runs" from
  "thing that talks to it".

## 5. Labels

- **Full official service names with vendor prefix**: `Amazon CloudFront`,
  `AWS WAF`, `Amazon Simple Storage Service (S3)`. Not `CloudFront`, not `S3`.
- Centred below the icon, dark, wrapping onto multiple lines where needed.
- Actor labels are lower-case: `internet users`, `branch users`, `API consumers`,
  `systems`.
- Application components get functional names, not product names: `User
  Experience Platform (UXP)`, `API layer/business components`.

## 6. Edges

- Thin grey orthogonal lines, small solid arrowheads.
- **Mostly unlabelled** — the numbered comments carry the semantics instead. This
  is a deliberate trade: labels on every edge is the *other* valid style, and
  mixing them produces the crowding this reference avoids.
- One coloured edge (green, RDS primary → secondary) where the relationship
  differs in kind from data flow.
- Arrows cross container boundaries cleanly rather than stopping at them.

## 7. Layout

- Left-to-right: actors → edge security → gateway → VPC → compute → data.
- External actors stacked vertically at the far left, outside the cloud.
- Shared services (Secrets Manager, ECR, CloudWatch) on their own row above the
  compute box, inside the VPC.
- Generous whitespace. No label collides with another or with an icon.

## What the skill can produce — closed, as of 2026-08-26

This section used to list what the generator had no slot for: title, subtitle,
thesis sentence, footer, review date, the annotation panel, numbered badges,
non-AWS actor icons outside the cloud boundary, a grey fill-only logical grouping,
an AZ label repeated top and bottom. **All of it ships.** The spec format grew
`title` / `subtitle` / `intent` / `reviewed` / `annotations`, `external: true`
draws a flat actor glyph outside every container, `emit()` repeats the AZ label at
the bottom of the band, and `groups.kind: generic` draws the grey fill-only
logical grouping. `validate.ts` treats a missing title, subtitle, intent or
annotation as an **error**, so the frame cannot silently regress.

`DiagramStyleConformance` moved 0.32 → 0.92–0.95 across that work. Two things
that made it up are worth keeping separate, because only one is a real
improvement: the generator gained the frame (real), and the rubric gained an
anchored scoring table (a measurement fix — see `evals/reference/README.md` for
the negative control that keeps it honest).

The row is still **excluded from the exit code**, and the reason has changed. It is
not that the check is always red; it is that a single vision call over a whole-page
render is the least reproducible layer in the stack, and it should not be able to
fail a build on its own. It is printed every run and it is read every run.

Live limitations, verified rather than assumed: single-row auto-layout places edge
labels at the midpoint, which collides with the next icon in a row of 78 px
stencils; edges cannot route around obstacles; container overflow is dumped on the
root layer.

One frame element was **not** shipping despite this section claiming the container
language was complete: subnet containers carried no badge at all. `groupStyle` asked
for `grIcon=mxgraph.aws4.group_private_subnet` and `...group_public_subnet`, and
neither name exists — the aws4 set ships exactly one subnet badge, `group_subnet`.
draw.io renders an unresolvable `grIcon` as *nothing*, not even the blank coloured
square an unresolvable `resIcon` gives you, so the border and label looked right and
the badge was simply absent. Every diagram with a subnet, across every iteration,
was missing it, and group 3 of the rubric asks for exactly "border style plus a
badge". Fixed to `group_subnet` for both kinds, told apart by colour, which is how
AWS's own style distinguishes public from private in any case.

Nothing could see it. `validate.ts` matched `resIcon=` only, and a container's badge
is `grIcon=`; the style judge sees a downsampled 3000 px render where a missing 20 px
badge is invisible; and the generator's own note fired on catalog membership, which
these were not. The check now tests **every** `mxgraph.aws4.*` reference in a cell
against the stencil list, with the library's four structural shape names exempted by
name — the narrow version of this check is what let the bug live.

## What the style judge can and cannot be trusted on

First run, `three-tier-web`: **0.32**, with a per-group breakdown. The two
headline findings are correct and verifiable from the source:

- No document frame — the spec format has no slot for a title, and there is none.
- No numbered annotations — likewise.
- Labels drop the vendor prefix: `ECS Fargate Service`, `RDS Database`,
  `CloudFront Distribution`. True, and fixable in `SKILL.md` today with no
  generator change. The cheapest real improvement on this list.

Two of the six group scores were marked down on things that are not so:

| Judge's claim | Actually |
|---|---|
| "The Application Load Balancer icon appears as a line-art circle rather than a filled coloured square" | `shape=mxgraph.aws4.resourceIcon;resIcon=mxgraph.aws4.elastic_load_balancing` — a filled square with a white glyph, confirmed by rendering the stencil directly |
| "no distinct `aws` badge on the outer AWS Cloud boundary" | the group carries one; the same reason says *"only an 'AWS Cloud' badge"* two paragraphs earlier |

That is roughly 1.0 of the 6-point breakdown resting on misread pixels, on a
2975 px-wide render — the same downsampling blind spot that let two blank icons
through on `coinbase-low-latency` (`README.md`).

**So scope what you believe.** The style judge is reliable for presence/absence of
large structure — is there a title, is there an annotation panel, do labels carry
vendor prefixes — because those survive downsampling or are readable as text. It
is not reliable about how an individual icon is drawn. Icon-level facts come from
the `.drawio` source, exactly, for free.
